# Lambda Managed Instances lifecycle conformance

**Design, updated November 26, 2026.** Dated facts about the open PRs and branches are collected in [Stack status](#stack-status). The rest of this document describes the design; where it says what a PR still has to do, it describes the stack as of November 26.

Lambda Managed Instances (LMI) can run overlapping invocations in one execution environment and reuse workers across requests. A platform timeout can end an invocation while user code is still running. Durable execution history can show the persisted outcome, but proving invocation isolation also requires knowing which request owned the work, when the SDK dispatched it, and what happened to the original worker and its peers. JavaScript, Java, and Python need the same acceptance rules across different runtime models. [Tracking issue #161](https://github.com/aws/aws-durable-execution-conformance-tests/issues/161)

## Scope

Add an opt-in, language-neutral `lmi-lifecycle` suite with seven required scenarios per supported runtime and a shared harness for live AWS runs. Preserve the existing ordinary-conformance entry points, including `--suite all`. Keep language-specific fixtures and regressions in each SDK. LMI OpenTelemetry and plugin conformance are deferred. The lifecycle contract requires observable isolation and bounded recovery. It leaves cancellation mechanisms to SDKs and makes no hard-termination guarantee for arbitrary user I/O. [Contract #193](https://github.com/aws/aws-durable-execution-conformance-tests/pull/193) · [Tracking issue #161](https://github.com/aws/aws-durable-execution-conformance-tests/issues/161)

## Required behavior

The table summarizes the contract merged in #193. Its evidence guide and requirement YAML hold the full assertions. [Contract #193](https://github.com/aws/aws-durable-execution-conformance-tests/pull/193)

| ID | Scenario | What the evidence must establish |
| --- | --- | --- |
| 1 | Native overlap | The original victim and peer belong to distinct durable executions and reach the barrier during observed overlap at the runtime’s sharing boundary. Each dispatches its own successful `record-marker` step checkpoint during overlap. The stored results match distinct fixture expectations for their respective invocations. |
| 2 | Normal return | The root succeeds and the wrapper returns. A victim-owned checkpoint probe at or after actual wrapper return is rejected, and the SDK dispatches no new request for the closed invocation. |
| 3 | Deadline during step | Controlled work is in flight at the platform timeout. Admission closes within `admissionMs` of the timeout, both probes are rejected at or after closure, and the task exits within `cleanupMs` of the timeout. |
| 4 | Peer recovery | Establish the overlap and deadline observations. The original peers occupy every other native slot through recovery and show progress before timeout and again by recovery. An independent recovery request records `worker_recovered` in the original environment under the selected worker policy within `recoveryMs` of timeout, and succeeds. |
| 5 | Suspension and retry | The service resumes the same execution after `PENDING`. Replay preserves operation identity, including unnamed operations, and reuses stored successes and failures without rerunning completed bodies. An incomplete operation has a failed attempt followed by success, with the expected side-effect counts. |
| 6 | Warm reuse | The warm request runs in the same environment, worker and process after the victim invocation. Victim-owned late activity occurs during the warm request and precedes the victim task’s exit. |
| 7 | Normal failure | The root fails and the wrapper returns the failure. Preserve the outcome and apply the same post-return checkpoint rules as in case 2. |

The merged #193 contract makes the selected victim’s operation probe optional at or after actual wrapper return. A supplied outcome is retained. If admission had closed before wrapper return, an observed `ACCEPTED` probe fails the case. An omitted or rejected operation probe is still allowed. The rejected checkpoint probe at or after wrapper return remains required. A separate late SDK dispatch fails even when the checkpoint probe reports rejection or service history lacks the request. An earlier dispatch may settle after closure. Cases 2 and 7 also require a separate victim task exit at or after root completion. A raised wrapper and a returned failure are distinct boundaries. [Contract #193](https://github.com/aws/aws-durable-execution-conformance-tests/pull/193) · [Closed disposal draft #200](https://github.com/aws/aws-durable-execution-conformance-tests/pull/200)

## Architecture

| Layer | Responsibility |
| --- | --- |
| Contract and validator | The catalog defines roles, minimum native concurrency and scheduling constraints. The version 1 JSON Schema describes final evidence. The executable Python validator checks structure and semantics for observation and final validation, including ownership, causal order, replay, coverage and retirement. Verdicts for collected runs come only from adjudication, which applies these rules to the collected evidence. |
| Coordinator | Runs collection. It admits the manifest, budgets and schedules cases, journals dispatch, freezes and retains evidence, and audits physical retirement to decide whether a target can be reused. It never decides conformance, so its results carry collection statuses and never `PASSED`. Its collector, the adapter, is the built-in shared AWS driver configured by the deployment's recorded fixture binding. It runs against fake adapters in tests without embedding AWS transport logic. |
| Shared AWS driver | The only collector for shared runs. It deploys persistent concurrency-1 and concurrency-2 targets, drives barriers and faults, invokes fixtures, and normalizes service history and S3 ledger records. It manages run-scoped cleanup and persistent retirement fences. `SharedAdapter`, `ScenarioDriver`, `build_evidence`, `configuration_identity` and the `ScenarioAdapter` protocol are internal, so they can change without edits to an SDK's binding; an SDK-owned suite's custom collector implements `ScenarioAdapter` against its pinned package revision. |
| SDK fixture binding | Each SDK keeps its real public-API handlers, observation hooks, build and stage script, and describes its deployed fixture with the data-only [fixture binding](#fixture-binding), from which conformance derives everything else it needs. |
| Reusable workflow | Runs the harness and trusted cloud jobs, owns OIDC and account verification, refreshes credentials, and collects cleanup results, artifacts and summaries. SDK callers supply a stage script that builds and deploys the tested SDK artifact, and pin the workflow and package to the same revision. |

The runtime profile describes real placement. Node.js overlap occurs within a worker, Java overlap within a JVM, and Python overlap across worker processes in one environment. Python warm reuse establishes sequential reuse of a specific process. The scheduler reserves capacity, while placement assertions use observed environment and worker identities. Use a new deployment profile when the scenario needs incompatible runtime or function settings. [Contract #193](https://github.com/aws/aws-durable-execution-conformance-tests/pull/193) · [Coordinator #195](https://github.com/aws/aws-durable-execution-conformance-tests/pull/195) · [AWS driver #219](https://github.com/aws/aws-durable-execution-conformance-tests/pull/219) · [Scenario driver #220](https://github.com/aws/aws-durable-execution-conformance-tests/pull/220) · [Workflow #190](https://github.com/aws/aws-durable-execution-conformance-tests/pull/190)

## Fixture binding

Each SDK describes its deployed fixture with a data-only `FixtureBinding`, usually loaded from checked-in JSON with `FixtureBinding.load(path)` and attached to the `RuntimeDefinition` it passes to the deployment. Validation fails closed:

| Field | Values |
| --- | --- |
| `bindingVersion` | 1. |
| `fixtures` | Fixture names, as non-empty strings, keyed by the seven catalog scenarios and the `peer`, `recovery` and `warm` roles. An unknown key rejects the binding. A missing scenario key reports that scenario `NOT_IMPLEMENTED`, and a missing role key reports the scenario that launches the role: `peer` and `recovery` for peer recovery, `warm` for warm reuse. Native overlap launches every role from its own fixture. Other cases still run. |
| `failureErrorType` | Non-empty error type name, such as Python `ValueError` or JavaScript `Error`. |
| `workerIdentity` | `process` or `worker`. |
| `suspension` | `callback` (default) or `wait`. In `callback` mode the fixture names its suspension callback `completion`, which the built-in driver looks for. |
| `callbackPayload` | `marker` (default; the marker's UTF-8 bytes) or `json-marker`. |
| `recoveryPolicy` | `reuse-worker` (default) or `replace-worker`. |
| `replayEffects` | A non-empty array of entries with `operation` (non-empty), positive integer `count` and optional `values`, a non-empty array of distinct integers. Each operation appears in at most one entry, so a binding cannot give the same key two counts or mix an entry with `values` and one without for the same operation. The default is `success` 1, `failure` 1 and `retry` 2. The shared replay fixtures keep the stable operation names `success`, `failure` and `retry`, and lifecycle 5 finds its retry by the name `retry`; other entries cover any further operations whose effects a fixture records. |

The deployment records the binding under `fixtureBinding` next to the runtime model, handler, architecture and memory size. `make_manifest` copies the deployment into every plan, takes the plan's `runtime` from `runtimeModel` and each profile's `recovery_policy` from the binding, and `configuration_identity(deployment, key)` reconstructs the runtime from the deployment and adds the binding to the existing per-profile hash of selected deployment fields and that profile's function and concurrency. Conformance derives the rest:

- **Expected outcomes.** The `normal-failure` victim expects `FAILED` with the binding's `failureErrorType` and the message `expected:` plus its marker. The `deadline-during-step` and `peer-recovery` victims accept the statuses `RUNNING`, `SUCCEEDED`, `FAILED`, `TIMED_OUT` and `STOPPED`. Every other launch expects `SUCCEEDED` with its marker as the result.
- **Worker identity.** The ledger field that `workerIdentity` names.
- **Replay policy.** An entry with `values` gives one key per listed integer; an entry without `values` gives one key for the operation, whatever value a body reports. Allowances belong to durable operation IDs, and an ID's first body fixes the one key it may own. For each key, the first ID owns `count`, and an ID whose first body has a key that another ID owns expects 0. An ID whose first body names an operation that no entry lists, or reports an unlisted or non-integer value for an operation with `values`, also expects 0, so a binding lists every operation whose effects its fixtures record. A later body of an ID that repeats its first key counts against that allowance; one with any other key sets the ID's allowance to 0, so a repeated side effect cannot pass under a second ID. A key that never appears is reported missing. The existing replay-policy validation checks the result.
- **Profile verifier and configuration identity.** One verifier of the recorded `RuntimeDefinition` serves both the deployment manager and the live `Cloud.verify`, which still reads the function's actual configuration and scaling, so a target that drifted from the recorded deployment fails.

After admission, the built-in catalog collector therefore invokes no SDK callbacks. An SDK can still build the plan in the runner's process through `manifest_factory`.

## Execution and evidence

A run has two halves. Collection runs the cases on AWS and records what happened. Adjudication derives the verdict from that record alone. Collection never decides conformance, and adjudication never contacts AWS. [Coordinator #195](https://github.com/aws/aws-durable-execution-conformance-tests/pull/195)

1. Admit the manifest and retain a copy. Built-in collection first checks the deployment and binding, as listed under the CLI examples below. Every CLI mode claims an empty output directory with an exclusive `manifest.json` write, so simultaneous runs cannot share it. Validate catalog membership and bind each case to its declared profile, roles and budgets. Report declared `NOT_IMPLEMENTED` cases without dispatching them.
2. Schedule compatible cases against an unchanged target within its capacity. Exclusive cases require other owners to retire. The coordinator lets an adapter release its native capacity reservation after its requests are idle and reacquire it before controlled dispatch, while retaining target ownership. Built-in cases keep their reservations through callback lookup, automatic retries and retirement. Record the attempt in `attempts.jsonl` before dispatch and abort the launch if the write fails.
3. Run the selected invocations under bounded provisioning, placement, execution and collection phases. Correlate run and case IDs, request IDs, execution ARNs and worker identities. The shared driver journals a stable durable execution name before invoking and uses it for transport retries, including ambiguous responses. Service invocation timestamps and SDK lifecycle events establish different parts of the timeline.
4. Freeze each case's observations before releasing its faults. SDK request records can show attempts that service history cannot see, so retain them with lifecycle events and persisted history. The adapter must report [cumulative snapshots](#trust-boundary): the coordinator keeps the latest one as the case's evidence, without merging snapshots or checking that they agree, and still records every snapshot in the bundle. Host-monotonic coordination deadlines never become evidence. Each driver wait, including callback lookup, uses the remaining phase budget.
5. Release case-owned faults and audit outstanding executions, callbacks, requests and tasks. A cleanup request is evidence of an attempt to retire work. Positive settlement and ownership evidence are required before reuse. Preserve both behavioral and retirement failures. Profiles finish only after every case in the run has finished retirement. A profile is reported quiescent, which lets `finish` release its external lock, only if its target is not quarantined and no adapter phase in the run was interrupted, because an interrupted task may have used, or may still use, any target.
6. After every target is released or quarantined, write the frozen observations and separate cleanup evidence to `collected-evidence.json`, read the file back and adjudicate it against the original admitted cases. Adjudication compares SDK request records with lifecycle events and persisted history and applies the declared behavior budgets. `attempts.jsonl` and `results.jsonl` are the run journals: a `COLLECTED` row in `results.jsonl` awaits the verdict row that adjudication appends. Every CLI mode writes final per-case results to `evidence.json`, coverage to `coverage.json`, and JSON and JUnit reports. `evidence.json` holds the final result even if a final journal append fails. Strict acceptance exits nonzero for failed, missing or unimplemented required cases. [Contract #193](https://github.com/aws/aws-durable-execution-conformance-tests/pull/193) · [Coordinator #195](https://github.com/aws/aws-durable-execution-conformance-tests/pull/195) · [Scenario driver #220](https://github.com/aws/aws-durable-execution-conformance-tests/pull/220)

```sh
# Collect with the built-in shared collector, then adjudicate the collected evidence.
durable-execution-conformance lmi-lifecycle --manifest manifest.json \
  --collect --output lmi-collection

# Adjudicate a saved bundle again, without an adapter or AWS credentials.
durable-execution-conformance lmi-lifecycle --manifest lmi-collection/manifest.json \
  --collected-evidence lmi-collection/collected-evidence.json --output lmi-adjudication
```

The CLI takes `--manifest` and exactly one of `--collect` and `--collected-evidence`.

- **Built-in collection** with `--collect`, or `collect_and_adjudicate` with neither `suite` nor `adapter_factory`, is a catalog run with the built-in collector. Before it claims the output directory, it requires `sdk.deployment` with its runtime fields, a valid fixture binding, a verified `conformanceRevision`, a `runtimeModel` equal to the plan's runtime, and a non-empty `sdk.artifacts_dir`, which a direct `collect_and_adjudicate` call must give as an absolute path. With `--collect`, the CLI resolves a relative artifact directory first, as `runner.run` does before it calls `collect_and_adjudicate`. Collection through an SDK-owned suite's custom collector skips these deployment checks, but its manifest is still validated.
- **Re-adjudication** with `--collected-evidence` uses the saved manifest and bundle as they are. It applies neither the built-in collection checks nor path normalization, imports no SDK code and contacts no AWS service. The CLI recognizes only the shared catalog. A bundle from an SDK-owned suite is re-adjudicated against its admitted manifest through the library: `load_manifest(path, suite=suite)` and `load_collected_evidence(path)`, then `adjudicate_collected_evidence(..., suite=suite)` and `build_report(..., suite=suite)`.
- **Programmatic entry points** are `make_manifest(deployment, coverage, directory, *, artifact_id, conformance_revision)`, `runner.run(deployment, directory, *, manifest_factory)` and `collect_and_adjudicate(manifest, *, audit_dir, suite=None, adapter_factory=None)`. `suite` and `adapter_factory` go together. Both select an SDK-owned suite with its own collector, neither selects a catalog run with the built-in collector, and one without the other is rejected before the audit directory is claimed, because the shared driver is tied to catalog requirement IDs, such as its deadline requirements and the lifecycle 5 resume rule. The engine validates the manifest, claims the audit directory, publishes declared skips, and calls the factory with a deep copy of the admitted manifest only if a case is active. If the run is cancelled, it attempts to save and adjudicate the results already emitted, then re-raises the original cancellation even if that preservation fails.

Adjudicating a saved bundle again is a tool for debugging, investigating a reported verdict and developing rules. It is not a verification step, and CI does not run it. What it can establish follows from the [trust boundary](#trust-boundary). [Coordinator #195](https://github.com/aws/aws-durable-execution-conformance-tests/pull/195)

## Trust boundary

The harness trusts its own collection path and tests the SDK. Adjudication trusts collection, collection trusts the adapter, and only the SDK under test is untrusted. [Coordinator #195](https://github.com/aws/aws-durable-execution-conformance-tests/pull/195) · [AWS driver #219](https://github.com/aws/aws-durable-execution-conformance-tests/pull/219) · [Evidence #222](https://github.com/aws/aws-durable-execution-conformance-tests/pull/222) · [Scenario driver #220](https://github.com/aws/aws-durable-execution-conformance-tests/pull/220)

| Component | Trust |
| --- | --- |
| Coordinator and adjudication | Trusted. Adjudication assumes that the coordinator wrote `collected-evidence.json`, that the file has not been modified, and that the manifest passed with it is that run's own `manifest.json`. |
| Adapter: the built-in shared AWS driver with the recorded fixture binding | Trusted. The coordinator records what the adapter reports about a case's launches, resources, observations and cleanup without checking that the reports agree with each other, with admission or with other cases. It still uses them together to identify and settle SDK work. |
| SDK fixture and artifact | Untrusted. Their output is the behavior under test. |

**Collection trusts the adapter.** Only AWS Lambda Managed Instances is supported. For shared runs the built-in shared driver is the only collector: there is no `--adapter module:factory` extension point and no dynamic import, and collection trusts the pinned conformance package plus the validated fixture binding recorded with the evidence. This repository tests and reviews the driver and the outcomes, identity and replay policy it derives, and each SDK repository reviews its binding data. SDK stage scripts still start the run, which is a contract boundary, not a sandbox. Fake adapters stand in for the driver in the coordinator's tests. A custom collector is accepted only for an SDK-owned suite. It is SDK code that collection then trusts as its adapter; its results use the suite's own namespace and cannot fill shared coverage, so shared runs keep the boundary above.

**Adjudication trusts collection.** It judges behavior again with the current rules, but trusts the recorded collection status and the facts only collection can observe. It runs the independent physical retirement audit only where a behavior verdict depends on retirement facts: the lifecycle 2/7 allowance for retries proven during retirement and, from #222, the cutoff obligations through `audit_cutoff`. Otherwise it trusts the coordinator's audit, which gates target reuse.

**Which checks stay.** A check stays if, with a correct adapter, it can report SDK behavior or incomplete collection that no other kept check reports in time for the same decision. Every other check goes:

- a check that only a faulty adapter can fail, such as a check that the collected identity matches admission or that a journal update does not rebind a launch's request;
- a check that fails only because a value that the snapshot contract below lets change has changed, such as a reselected retry operation;
- a check whose failures with a correct adapter a kept check on the latest snapshot also reports in time for the same decision, such as the settlement and retirement-time checks that the retirement audit repeats on the cumulative retirement snapshot.

A check against an independent expectation stays even when the value it reads is recomputed, such as a side-effect count above the binding's expected count. Cross-case ownership claims go under the third case. A correct driver can provisionally journal an SDK-reported request ID that collides with another case, the reporting case's own audit detects that misattribution, and the claim would also quarantine the other case.

Under this rule, collection and adjudication keep:

- phase budgets, interrupted adapter phases, collection errors and failed observation or control publication;
- the evidence that collection is complete: the driver verifies each fixture stream's seal and capture sequence, and for runtime evidence the validator requires the lifecycle, SDK-request and history watermarks to cover the audited window. A partial snapshot clears its watermarks, and #222's controls-only retirement requires none;
- `retire` not proving quiescence;
- cleanup snapshots whose owned inventories differ from the frozen observations, which require the independent retirement audit of the final retirement evidence;
- a journaled launch that may have dispatched but has no identified invocation request, which keeps its target quarantined because no snapshot can show that it ended. A launch whose Invoke the service definitively rejected never ran and is exempt;
- `_cleanup_record_errors`, which reconciles the native owner, binding, settlement and observation window of every SDK record in every retained snapshot with the final settlements. Collection uses its `INCOMPLETE` findings to gate target reuse. When frozen observations exist, adjudication runs the check again on its own inputs and also reports its `ASSERTION` findings;
- adjudication's check that the frozen observations cover every identified journaled launch that is not deferred. A correct driver journals a service retry when it can bind the retry's `WRAPPER_ENTER` record to its launch, which can be after the freeze even when the platform start preceded the cutoff, so this check can be the only one that reports a retry that started before the cutoff;
- the check in #210's `_identity_errors` that `selectedRequests` covers every role the manifest declares, because a declared role that was never dispatched leaves no journal entry;
- the independent physical retirement audit, `validate_retirement_evidence` on the retirement snapshot or `validate_observed_retirement` on the normal path, including its checks that each invocation and execution settlement covers its recorded activity and that retirement ends no earlier than any settlement or its own cutoff;
- every behavior rule, except comparisons across snapshots that the rule above removes.

As an exception, adjudication keeps comparing the evidence runtime with the manifest's, because an SDK-owned suite's custom collector, or a capture made before the built-in collector, reports its own runtime, and a mismatch would otherwise produce a verdict under the wrong label. The built-in collector takes the runtime from the plan, and built-in collection checks before it claims the output directory that the deployment's `runtimeModel` equals the plan's runtime.

Quarantine for unproven retirement and the driver's S3 fences are unchanged. The check-by-check list of removals belongs in the #195 and #210 descriptions.

**Cumulative snapshots.** The adapter must report cumulative snapshots. A later observation, partial, cleanup or retirement snapshot of a case can add records and fields, fill a previously unassigned association such as a null `observedDuringRequestId`, complete an attempt that was active at the cutoff, advance nonterminal statuses, refine a provisional fixture-sourced time as earlier activity is observed, replace fixture-sourced times with platform measurements, and renumber sequences without changing any request's relative order. It never removes an observed record, execution or resource, and never changes an identity or a terminal fact. Derived summaries, such as `replay.retry`, `replay.sideEffects` and `replay.expectedBefore`, are recomputed from each snapshot's records: a partial or pending snapshot may omit them, and a later snapshot may select a different retry operation. The observation cutoff, `observationEndedAtMs`, never moves earlier. Other collection metadata, such as watermarks and collection errors, describes the collection window of the snapshot that carries it: the watermarks must cover the window being audited, and a frozen deferral is proved against independent retirement evidence. The coordinator keeps the latest observation snapshot as the case's evidence without merging snapshots, and still records every observation and cleanup snapshot in the bundle, because the rules read them. The current driver meets the rule for ledger records, because every phase reads through the case's one `Cloud` instance, which reads each record once and caches it; the rest is #222 and #220 work, listed under follow-ups.

**Consequence.** Driver and binding bugs are caught only by tests and review: the driver's in `tests/lmi_driver/`, and each binding's in its SDK repository. A driver that drops observations or cleanup facts, or a binding that misdescribes its fixtures, failure type or replay effects, can produce a false pass, or let an unretired target be reused, without any finding.

## Target ownership and failure recovery

In-process quarantine prevents the coordinator from dispatching to a target whose retirement is unproven. A scheduler serves one run; sharing it across runs is not supported, so it has no in-process recovery and a quarantined target stays quarantined for the rest of the run. When a profile is not quiescent, the adapter's `finish` must keep its external run ownership in place until recovery. The driver's S3 fence persists across runs and protects a target if cleanup fails or the process is interrupted. The driver creates each fence conditionally with a unique acquisition token. After a lost acknowledgement of a known single submission, reading back the exact record can resolve the acquisition; if the transport reports retries, ownership stays unresolved. Release verifies the fence's resource, run, commit and acquisition token, then deletes it with the observed ETag, so a fence replaced after that check is not removed. Unknown ownership or incomplete retirement requires explicit recovery outside the run before reuse. Other targets can continue. [Coordinator #195](https://github.com/aws/aws-durable-execution-conformance-tests/pull/195) · [AWS driver #219](https://github.com/aws/aws-durable-execution-conformance-tests/pull/219)

The workflow's fixed concurrency group serializes cloud jobs within each caller repository with cancellation disabled. Separate SDK callers need isolated capacity because GitHub concurrency groups are repository-scoped. Fork and Dependabot changes remain on the unprivileged harness path. The workflow collects artifacts and attempts cleanup on failure so operators can distinguish assertion failures, evidence gaps and unresolved retirement. [Workflow #190](https://github.com/aws/aws-durable-execution-conformance-tests/pull/190)

## Tradeoffs

- SDK-only suites can exercise language-specific races directly, but duplicate placement and evidence checks. Shared validation gives these runtimes one acceptance contract while preserving SDK-specific fixtures.
- Per-case deployment simplifies isolation but repeats provisioning and makes reuse across scenarios harder to measure. Persistent profiles reduce deploys, with leases, ownership and retirement fences needed to keep reuse safe.
- Service-history-only checks are simpler to collect but miss attempted transport sends and worker-local behavior. A normalized evidence ledger lets adjudication run the same assertions without AWS access at the cost of requiring trustworthy instrumentation and complete collection. [Tracking issue #161](https://github.com/aws/aws-durable-execution-conformance-tests/issues/161) · [Evidence #222](https://github.com/aws/aws-durable-execution-conformance-tests/pull/222)
- A generic `--adapter module:factory` extension point lets each SDK compose its own collector, but it puts SDK code on the trusted collection path and needs a dynamic import. A data-only binding keeps the collector in this repository and makes the SDK-specific facts reviewable data that `configuration_id` hashes. An SDK that needs other collection behavior uses an SDK-owned suite.
- Cross-checking the adapter's reports at run time catches some driver and binding bugs, but it takes a large share of the coordinator and its tests, and it cannot catch an adapter that is consistently wrong. Trusting the adapter keeps collection simpler and leaves its correctness to tests and review in this repository and in each SDK repository. [Coordinator #195](https://github.com/aws/aws-durable-execution-conformance-tests/pull/195)
- Re-running collection integrity checks during adjudication could detect inconsistent edits to a bundle, but it cannot prove the bundle is unmodified and it duplicates checks the coordinator already makes before reuse. Trusting coordinator-written bundles keeps adjudication simpler. Either way, a saved bundle supports debugging, not verification. [Coordinator #195](https://github.com/aws/aws-durable-execution-conformance-tests/pull/195)
